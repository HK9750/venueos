# Data Model and Migrations

## Global Conventions

- Primary IDs are UUIDv7/UUID-compatible opaque identifiers generated by the
  application or database consistently.
- Every tenant-owned table has non-null `organization_id`, indexed with common
  lookup keys. Foreign keys include/validate tenant ownership where practical.
- Mutable aggregates have integer `version` for optimistic concurrency.
- Timestamps use `timestamptz`; business decisions use database time in critical
  transactions. Local timezone is stored separately as an IANA name.
- Money uses `bigint` minor units and three-letter currency code. Constraints reject
  negative values except where a clearly named adjustment field allows them.
- Human-facing normalized email/code/slug fields have deliberate case-insensitive
  uniqueness using normalized columns or `citext` where accepted.
- State/status fields use checked text or PostgreSQL enums only when migration cost
  is understood. Application transition functions remain authoritative.
- JSONB is reserved for provider payload references, immutable snapshots, geometry,
  or flexible metadata with documented schema/size. Query-critical data is typed.
- Soft archive is used for referenced business entities. Hard deletion is limited
  to eligible ephemeral/PII data under a retention job.
- No generic polymorphic foreign key where a real relation is required. Audit and
  event subject references are the intentional exception.

## Platform Reliability Tables

| Table | Purpose |
|---|---|
| `idempotency_records` | organization/principal/operation/key unique, request fingerprint, state, locked expiry, response status/body/reference, retention expiry |
| `outbox_events` | event ID, tenant, aggregate/version, type/schema version, payload, occurred/available time, attempts, lease/published/dead-letter metadata |
| `inbox_messages` | source + message ID unique, payload reference/hash, received/processed status and error |
| `jobs` | type, tenant, dedupe key, payload/version, priority, run time, attempts/max, lease owner/expiry, state/error |

Claim jobs/events with `FOR UPDATE SKIP LOCKED`, a lease expiry, bounded batch size,
and commit before execution. A unique dedupe key prevents logically duplicate jobs.
Large/raw provider bodies can live in encrypted object storage with hash/reference,
subject to retention.

## Index Strategy

Every index must name a query or constraint it supports. Expected composites include:

- tenant + ID for all tenant resources;
- tenant + status + created time for operational lists;
- session + state + seat/pool for availability;
- active hold expiry partial index;
- order number/customer/provider reference search under tenant;
- payment/refund provider IDs unique;
- jobs/outbox by state + available/run time + priority;
- scan session + scanned time and ticket history;
- webhook endpoint + state + next attempt;
- audit tenant + occurred time plus subject/actor secondary indexes.

Use `EXPLAIN (ANALYZE, BUFFERS)` against realistic cardinality before launch. Avoid
indexes on low-selectivity fields alone and unbounded `%term%` search; use trigram or
search projection if support search requires it.

## Retention and Partitioning

Initial tables stay unpartitioned until evidence warrants complexity. Likely future
partition candidates are audit entries, realtime events, scan attempts, provider
events, webhook deliveries, and idempotency records. Partition by time while tenant
remains in indexes and access policy.

Indicative retention, finalized by legal/product decision:

- realtime replay: hours to days;
- idempotency full response: 24–72 hours, key tombstone longer where needed;
- raw provider/webhook payloads: shortest operational/legal period;
- delivery logs: months with redacted recipient;
- financial/order/audit records: jurisdictional retention;
- exports and offline manifests: days, automatically deleted;
- expired invitations/socket tickets/rate data: short TTL and purge.

## Migration Policy

Use expand/migrate/contract for zero-downtime changes:

1. add nullable/new structures compatible with old code;
2. deploy dual-read/write or backfill logic;
3. backfill in resumable bounded batches with progress/metrics;
4. validate constraints/indexes online where supported;
5. switch reads and observe;
6. remove old path in a later deployment;
7. contract schema only after rollback window closes.

Never combine a destructive migration with code that requires the new state in one
irreversible deploy. Large indexes use concurrent creation outside a transaction.
Migrations have explicit lock/statement timeouts and fail safely if exceeded.

Each migration review documents forward compatibility, rollback/roll-forward,
expected locks/duration, backfill, disk growth, replication impact, and verification
query. CI applies migrations from empty and from the latest supported production
snapshot, then runs schema/query tests.
